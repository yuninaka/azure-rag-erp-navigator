# Step 6: golden_qa精度評価スクリプト

関連Issue: #1

## スコープ

Step 1〜5で構築したRAGパイプライン（`generate_answer`）を対象に、golden_qa形式のテストケース
18問でキーワード網羅率による精度評価を行う。過去のNeo4jグラフRAG検証と同じ評価手法を採用し、
直接比較できるようにした。3つのチャンク分割方針（`fixed_512`/`fixed_256`/`heading_aware`）
それぞれで全問を実行し、方針ごとの精度差を比較する（当初からの検証目的の核）。

## 指標の選定

「キーワード網羅率」のみを実装し、RAGAS（LLM-as-judgeによるfaithfulness/answer_relevancy等）は
今回見送った。理由: RAGASは追加ライブラリ依存に加え、評価のたびに追加のLLM呼び出し（課金）が
発生する。過去のNeo4j検証もキーワード網羅率で評価しており、同一手法での比較を優先した。

## 実装物

- `eval/golden_qa.jsonl`: 18問。ERPNaviの5マニュアル・FAQ・トラブルシュート事例集の
  全カテゴリから出題（`category`フィールドでモジュール横断の内訳集計が可能）
- `eval/metrics.py`: `keyword_coverage`（純粋関数、単体テスト済み）
- `eval/dataset.py`: `load_golden_qa`（JSONL読み込み、純粋関数、単体テスト済み）
- `eval/run_eval.py`: 3戦略×18問を`generate_answer`（本番と同じロジック）に通し、
  結果を`eval/results.json`に保存する評価スクリプト。評価用セッションは質問ごとに使い捨て
  （`eval-{strategy}-{id}-{uuid}`）にし、通常の会話履歴と混ざらないようにした

## テスト方針

`keyword_coverage`と`load_golden_qa`は純粋関数のため単体テスト済み。`run_eval.py`本体
（配線部分）は単体テスト対象とせず、実リソースに対する実行で動作確認した（下記参照）。

```bash
uv run pytest tests/test_eval_metrics.py tests/test_eval_dataset.py -v
```

## 実リソースでの評価結果（2026-09-07）

```bash
uv run python eval/run_eval.py
```

| チャンク分割方針 | 平均スコア |
|---|---|
| `fixed_512` | 1.000 |
| `fixed_256` | 0.972 |
| `heading_aware` | 0.944 |

18問中16問は3戦略とも満点だった。差が出たのは以下の2問のみ。

- **fixed_256 / q14**（新規仕入先登録の必須チェック）: 0.50。回答は「反社会的勢力チェックリストとの
  照合」を正しく説明していたが、期待キーワードの一つ「コンプライアンスチェック」（原文の用語）を
  使わずに言い換えていたため未マッチ
- **heading_aware / q15**（支払サイト変更の遡及適用）: 0.00。回答は「既存の買掛金には適用されません」
  と内容は正しいが、期待キーワード「遡及適用」という語自体を使わずに言い換えていたため未マッチ

## 評価データの修正（実施済み、golden_qaのバグ）

初回実行時、以下2問が3戦略とも異常に低いスコアだった。回答文を確認したところ、RAGの回答自体は
正しく、`expected_keywords`の表記が実際の回答と噛み合っていないgolden_qa側のバグと判明したため、
修正して同じ回答文で再採点した（追加のAzure OpenAI呼び出しは発生させていない）。

- **q05**（SSO連携の注意点）: 期待キーワードに`"SAML"`を指定していたが、回答は`SAML`という
  略称ではなく`IdP`（source側にも登場する同義語）で説明することが多く、3戦略とも0.50止まりだった。
  `"SAML"` → `"IdP"`に変更し、3戦略とも1.00に
- **q15**（支払サイト変更の遡及適用）: 期待キーワードを`"遡及適用されず"`（活用形まで固定）に
  していたため、回答が`"遡及適用されません"`という自然な言い換えをしただけで不一致になっていた。
  活用語尾を含まない`"遡及適用"`に変更し、fixed_512/fixed_256は1.00に改善（heading_awareは
  上記の通り別の言い換えでなお0.00）

## 考察メモ（Zenn記事用）

キーワード網羅率は実装が簡単で再現性も高いが、**同じ内容でも言い換えられると拾えない**という
弱点が、今回も（過去のNeo4j検証と同様に）具体的な形で観測できた。特にheading_aware/q15の
ケースは、golden_qa修正後もなお言い換えで引っかかった実例であり、「手法の限界」であって
「RAGの回答品質の問題ではない」ことを、実際の回答文を読んで確認したうえで判断した。

チャンク分割方針間の差（1.000 / 0.972 / 0.944）は、この18問・この評価手法の範囲では
僅少であり、「方針によって大きく精度が変わる」とまでは言えない。ただし今回のダミーデータ・
質問数（18問）は小規模なため、この差が方針そのものの優劣を示すというより、個々の生成の
言い回しのブレに起因する可能性が高い。より確度の高い比較には、質問数を増やす、または
LLM-as-judge等の言い換えに頑健な指標を併用することが望ましい。
